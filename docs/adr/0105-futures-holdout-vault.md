# ADR-0105: Futures holdout vault — family-wide locked period, data-layer enforcement, human authorization, one evaluation per registration

- **Status**: accepted
- **Date**: 2026-11-21

## Context

C6c (PRD §13: "holdout vault: locked temporal partition, authorization token, persistent open
counter, fixed evaluation protocol, access log, unauthorized calls fail") is the last C6 stage.

The owner's binding decisions:

- **Family-wide.** One protected date range applies to the whole declared futures universe: ES, NQ,
  YM, RTY and NKD.
  - Any run that uses a protected instrument inside that range is controlled.
  - Creating another trial family does not bypass it.
  - A root-specific vault is allowed only for explicitly single-instrument research that uses no
    cross-instrument feature.
- **The period must not have been exposed.** Locking data later does not make it unseen. The
  exposure audit of 2026-11-19 found:
  - strategy-level exposure only on ES in 2024: 2024-01-02 to 2024-06-28, plus a DSL parity week;
  - the execution-simulator acceptance test walked one long contract across the full span of every
    root, which is a buy-and-hold path, not a strategy;
  - ingestion and integrity counts over the full span.

  The owner chose a **historical period with no strategy-level exposure**.
- **Enforcement is in the data-access layer,** not only in the CLI.
- **Tokens.** Authorization tokens are controlled by a human or an administrator, are stored
  outside the repository, and are never generated by the research agent.
- **Protocol.** The complete configuration hash is registered before authorization, each
  registration allows one evaluation, and every access attempt is logged persistently.
- **Lockout first.** The lockout is in place before any further experiment can reach the period.
  Failed and unauthorized attempts are auditable, and holdout results are not shown until the
  authorized evaluation has run.

## Decision

1. **The protected period.**
   - It covers Globex trade dates **from 2025-01-01, open-ended**: every later trade date,
     including data not yet ingested, is protected as well.
   - The universe is `ES, NQ, YM, RTY, NKD`.
   - Strategy work keeps everything up to 2024-12-31.
   - The declaration records the audit that justifies the period and its residual exposure (the
     buy-and-hold path and the integrity counts). It does not claim the period is unseen in any
     stronger sense.
2. **Declaration** (`vault.json`).
   - It is written in the store root **and** in the Crucible home. The guard enforces it if
     **either** copy exists, so copying the store or switching home does not lift it.
   - It holds `{vault_id, universe, start_trade_date, end_trade_date: null, scope: "family",
     declared_at, audit_ref, protected_datasets}`. The datasets are matched by root, from their
     dataset ids and manifests, never by family.
   - A declaration can only be widened: a later start, a narrower universe or deletion is refused.
     A `scope: "root"` vault requires an explicit single-root declaration, and runs under it refuse
     any cross-instrument operator (`cs_rank`).
3. **The guard** (`crucible.data.vault`). It is consulted by `ParquetDataStore.read` and
   `ParquetDataStore.data_path` for every dataset of a protected root.
   - A read whose `as_of` reaches the vault start (`as_of ≥ start of the first protected
     session`), or a whole-file `data_path` access, raises `VaultLockedError`.
   - The only exception is an active authorized evaluation (decision 5) whose registration covers
     that dataset.
   - Integrity and catalog tooling may still read whole files, in a `metadata` mode that returns
     only counts, hashes and date bounds, never rows. Every such access is logged.
   - Every attempt, allowed or refused, is appended to the access log. A log entry records the
     time, caller, purpose, dataset, `as_of`, the outcome and the registration id when there is
     one.
   - The guard is the same for the CLI, the MCP server and library calls. Nothing in the futures
     run path reaches a protected file without it.
4. **Registration** (`crucible vault register --config FILE`, open to anyone).
   - It records a `VR-<16 hex>` with:
     - the **complete config hash** and the dataset content hashes;
     - the candidate id (ADR-0103);
     - the evaluation window, which must lie inside the vault;
     - the requester;
     - the status, starting at `pending`.
   - Registration reads no protected data.
   - A config changed after registration has another hash, so it needs a new registration.
5. **Authorization and evaluation.**
   - `crucible vault authorize --registration VR-…` sets the status to `authorized`. It needs the
     admin token, supplied interactively on a TTY or through `CRUCIBLE_VAULT_TOKEN`.
     - It is verified against a **salted scrypt hash** stored outside the repository, in the home's
       `vault_admin` file, written by `crucible vault set-admin` with interactive TTY input only.
     - Crucible never generates, prints or stores the token in clear.
     - A non-interactive call without the variable is refused and logged.
   - `crucible vault evaluate --registration VR-…` runs the registered config exactly once.
     - It refuses a config whose hash differs from the registered one.
     - Inside the evaluation the guard admits the registered datasets up to the window end.
     - The open counter, which is persistent and never decremented, is incremented **before** any
       data is read, so a crash still consumes the evaluation.
     - The result is sealed as an ordinary futures run under `artifacts_root/VAULT/<VR-…>/`, and
       the status becomes `evaluated`.
     - A second `evaluate` of the same registration is refused and logged.
   - **Results stay hidden until evaluation.**
     - No command reports a protected-period number for a registration that has not been
       evaluated.
     - `vault status` shows only statuses, counters and the log.
     - `batch`, `walkforward`, `compare` and `trials` refuse any input that would read protected
       data, and `compare` and `trials` exclude vault artifacts from their pools unless asked
       explicitly after evaluation.
6. **Persistence.**
   - Registrations, the counter and the access log live in `vault.duckdb` in the Crucible home,
     with append-only semantics: no update or delete statement exists in the code, apart from the
     status transitions `pending → authorized → evaluated`.
   - `vault.json` in the store records the expected state of `vault.duckdb`: the vault id, the
     counter and the hash of the last log row. A database that is missing or behind that state is
     refused.
7. **Statistics.** A vault evaluation reports the C6a statistics, deflated by the family's
   `total_trials` and supplemented as in C6b. Its verdict stays `robustness_not_assessed`, because
   C7 decides the verdict.

## Residual risks (documented, not solved here)

- **Direct file reads.** Anyone with filesystem access can read the Parquet files outside Crucible.
  The vault guards Crucible's data path and logs it; it is not an access-control system. Keeping
  the admin token from the agent is the human's responsibility.
- **Ratio-adjusted series.** Backward ratio adjustment multiplies every pre-2025 bar by the product
  of the post-2025 roll ratios, which is one constant. Signals must be scale-invariant (ADR-0094,
  enforced), so that constant carries no usable information. It is still recorded as a residual.
- **The full-span simulator acceptance test now stops before the vault.** Its earlier full-span run
  is part of the documented exposure.

## Alternatives considered

- **Locking the last 12 months.** The owner ruled it out without an audit.
- **A prospective-only vault.** Strictly unseen, but it would wait for new data. The owner chose the
  historical option.
- **A vault per family.** It could be bypassed by creating a new family. Rejected.
- **CLI-only checks.** These can be bypassed through the library or MCP. Rejected.
- **Physically splitting the protected rows into another store.** It makes casual access harder, but
  it rewrites the processed datasets and their hashes. The data-layer guard and the double
  declaration were chosen instead. The split can be added later.

## Consequences

- **Research and evaluation are separated.** Every strategy and every bench now works on data up to
  2024-12-31. The protected period can be evaluated only through a registered, human-authorized,
  single-shot evaluation.
- **Bench tests must declare their window before 2025.** The full-span tests are narrowed.
- **Futures runs read up to the close of `window.end`.** They no longer use an open-ended `as_of`,
  so a pre-vault run passes the guard. The rows read are the same, and the real ES example is
  unchanged.
- **Rebuilding a continuous dataset of a protected root is refused once the vault is declared.**
  That rebuild reads the whole raw series. A maintenance path for ingestion is a later decision.
