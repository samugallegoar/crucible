# ADR-0107: Firm rulesets as sourced, hash-locked data with owner-only verification; attempt sequences, censoring and pass probability with an overlapping-attempt block bootstrap

- **Status**: accepted
- **Date**: 2026-11-21

## Context

C7a (ADR-0106) built the generic rule engine and tested it on synthetic rulesets only. C7b adds
real firms and attempt statistics.

**Firms.** The owner ruled that all six firms are integrated at once: FTMO, Lucid, Topstep, Apex,
MyFundedFutures and FundedNext.

**Rule data.**

- Every value is loaded from versioned, sourced rule data. The engine never hardcodes one.
- A ruleset stays `unverified` until the owner confirms it.
- Old versions are immutable.

**Attempts.**

- An attempt starts on an eligible trade date.
- Attempts overlap, so they are not independent. Uncertainty comes from a block bootstrap on the
  start sequence, with blocks at least as long as the longest attempt horizon.
- Attempts that are right-censored at the end of the data form their own class.

**Time.**

- Market data stays strictly before 2025-01-01, and the vault stays closed.
- A current ruleset applied to that data is labelled a counterfactual application.

**Verdict.** None before C7e, so no threshold appears here.

## Decision

### 1. Where firm rulesets live, and how immutability is enforced

**Files.** Each ruleset is a file `rulesets/prop/<firm>/<ruleset_id>.v<N>.yaml`.

- The file sits at the repository root, outside the `crucible` package. It is data, not engine.
- `rulesets/prop/<firm>/RESEARCH.md` records every URL, quotation, snapshot file and hash, plus the
  values the official pages do not state.

**Snapshots.** The page snapshots themselves are kept privately, outside the repository. The
repository carries only their hashes and the short quotations.

**The lock.** `rulesets/prop/INDEX.json` is generated by `uv run python -m tools.docgen --write`.
It lists every `(ruleset_id, version, ruleset_sha256)`.

- A test recomputes every hash against INDEX.json.
- Editing a committed version fails the test. A change is a new file, `v<N+1>`.
- A version number can never be reused, and INDEX.json is append-only. A test compares it with the
  copy in git history.

**What the content hash covers.** `ruleset_sha256` hashes the content without the `verification`
block. Verification is a fact *about* a content hash, not part of it, so confirming a ruleset
never changes its identity.

### 2. Owner-only verification

**The sidecar.** Verification lives in a sidecar file,
`rulesets/prop/<firm>/<ruleset_id>.v<N>.verification.yaml`. It holds:

- `ruleset_sha256`;
- `status: verified`;
- `confirmed_by`, `confirmed_at` and `confirmation_note`;
- the list of rule ids the owner checked, which must be every rule.

**Reading the status.** A ruleset is `verified` only when a sidecar exists, its hash matches the
content and every attribution is complete and non-synthetic. Anything else is `unverified`, and
every result carries the status.

**Who writes the sidecar.** Only `crucible prop confirm <ruleset>` writes it.

- The command follows the ADR-0105 rule: interactive TTY only, and refused otherwise.
- It shows each rule with its quotation and URL.
- The owner must type the first 12 characters of the content hash.
- The research agent cannot run it. Like `vault set-admin`, it is the owner's step.

### 3. Vocabulary extensions

The firms' official pages name rules that C7a's vocabulary cannot express exactly. Each new kind or
parameter is added with its own evaluator, hand-computed tests and a schema version bump. The list
is fixed after the research step, in the section "Vocabulary added in C7b" below.

Any rule still outside the vocabulary stays `not_modeled`, with the materiality the owner confirms.

### 4. The attempt sequence

**Signal.** A prop evaluation reads one futures run configuration (ADR-0095). The strategy signal
is computed once over the window plus its warm-up, exactly as `run_futures` does. Targets do not
depend on the account, so one causal signal serves every start.

**Start dates.** Every Globex trade date `d` in the window whose first scheduled bar is tradable is
a start date.

**Each start.** `simulate_attempt` runs from the open of `d`, with a fresh account per phase.

- `max_horizon_trading_days` (H) is required, and refused if it is shorter than any phase's
  `max_trading_days`. A calendar-day limit is converted per start with the session calendar.
- Contracts come from the run's targets, so the account's rules clip or reject what the run asks
  for. The configuration records how the strategy is sized.

**Outcome classes, per start, for the evaluation:**

| Outcome | Meaning |
|---|---|
| `pass` | Every evaluation phase passed. |
| `fail` | A hard rule was breached. |
| `timeout` | The firm's own time limit ended the phase. |
| `horizon` | H was reached unresolved. This is the analyst's horizon, not a firm rule. |
| `censored` | The data end before `d + H` and before resolution. |

`censored` is never counted as a pass or a fail.

**Funded phase.** For starts that pass, the funded phase runs inside the same horizon. Its outcomes
are reported descriptively: survival, breach, payouts made, payout total, and fees. C7b states no
probability for funded profitability.

### 5. Pass probability and its uncertainty

**Complete starts.** These are the starts whose horizon fits in the data, `d + H ≤ last date`. They
are never censored.

**The estimate.**

- **Point estimate:** `p = passes / complete starts`.
- **Bounds over all starts:**
  - `p_low = passes / all starts`, treating censored starts as fails;
  - `p_high = (passes + censored) / all starts`, treating them as passes.

  These bounds are reported beside `p`.

**Bootstrap.** A seeded circular block bootstrap (ADR-0103) runs over the complete starts in date
order.

- The seed is `bootstrap_seed(evaluation_id, statistic)`.
- The block length is `max(H, ceil(sqrt(n)))` trading days. One block therefore always covers
  starts whose attempts can overlap.
- The statistics are `p` and the mean net cash per attempt: trader payouts minus fees, the fees
  including resets only when the attempt policy buys one.
- A 95% percentile interval is reported for each.
- With fewer than two blocks (`n < 2 × block`), the interval is `unavailable`, with the reason. No
  number is invented.

**Information.** `effective_independent_attempts ≈ n / H` is reported, so a reader sees how little
independent information overlapping starts carry.

**Status of a probability.** It inherits `evaluation_status` (ADR-0106):

- `complete`: it is a pass probability under the modeled rules.
- `conditional_on_modeled_rules`: it is reported under the field name `conditional_pass_probability`
  and labelled so.
- `blocked`: the number is still reported, under the same conditional name, with
  `definitive: false` and the critical rules listed.

Every result also carries `counterfactual_application`, the ruleset `as_of` and its effective
dates, and `unverified_ruleset`.

### 6. Entry points and artifacts

**Command.** `crucible futures prop --config <run.yaml> --ruleset <file> --horizon H
[--payout-policy max_eligible|none]` writes a sealed artifact `PRP-<16hex>` containing:

- `attempts.parquet`, one row per start: outcome, phase outcomes, breached rule and time, days to
  pass, minimum buffer, payouts, fees;
- `summary.json`, with the statistics, the bootstrap record and the coverage;
- `ruleset.yaml`, the exact copy used;
- the manifest, with the run id basis, the candidate id (ADR-0103) and the ruleset hash.

**Other entry points.** `crucible prop list` lists the rulesets with their verification status. The
MCP tools `crucible_futures_prop`, `crucible_prop_list` and `crucible_prop_validate` are also added.
`crucible prop confirm` is not exposed over MCP.

**Trials.** A prop evaluation is an evaluation of an existing candidate, not a new strategy trial.
It does not change `submission_count` or `total_trials`. It is linked to the candidate id and the
family.

**Vault.** A window that reaches the vault is refused by the guard (ADR-0105).

### 7. Evidence, assumptions, conflicts and scenarios (schema version 2)

Every rule declares an `evidence` field. It takes one of four values:

- `official_quote`: an attribution to an official page.
- `owner_provided`: the owner supplied it.
  - Example: Lucid's per-side commission table, pasted by the owner, saved privately and hashed.
  - The attribution names the URL the owner read, or `null`, and the snapshot hash of the saved
    text.
- `assumption`: one of the defaults below, named, with its rationale.
- `conflict_resolution`: a genuine conflict was resolved to the more restrictive reading.

**Conflicts.**

- Two sources count as contradictory only after checking that they refer to the same firm, plan,
  account size, phase, platform and effective period. Otherwise they are separate variants.
- A genuine conflict keeps **both** sources in `conflicts`, with the selected value, the
  alternative value or values, and the rationale.
- Each alternative becomes a named **sensitivity scenario**. The scenario is the ruleset with one
  conflict switched. It is simulated and reported beside the primary result, never as an official
  plan.
- An unresolved conservative choice is never presented as an officially confirmed rule.

**Defaults.** Each default is applied only where the firm is silent, and recorded as an
`assumption`:

- "EST" means `America/New_York`, including DST.
- An unspecified observation frequency means intraday.
- A profit target is tested on closed balance.
- A trading day is a trade date with at least one executed trade.

**Day units are distinct.** `calendar_days`, `trade_dates`, `trading_days` and `winning_days`
are separate units. A rule names its unit.

**Unlimited, unknown and not modeled are distinct.** A value is one of three things:

- a number;
- `unlimited`, which the source must state;
- `unknown`, a value the sources do not give, which makes the rule `not_modeled`.

Numeric sentinels are refused.

### 8. Every rule is a typed declaration

Each rule kind's schema makes every one of these explicit, with **no defaults** for firm
semantics:

- the metric and its basis: closed balance, equity, or day P&L;
- the threshold or formula;
- the observation frequency: `intraday`, `eod` or `on_request`;
- the reset boundary and its time zone;
- the trigger comparison: `<=`, `<`, `>=` or `>`;
- the resulting action or state transition: `fail`, `soft_lock_until_reset`, `liquidate`, `block_entries`,
  `promote_phase`, `forfeit_excess` or `none`;
- the source, the effective dates and the evidence.

The engine has no firm-specific branches. A test asserts this (ADR-0106).

### 9. Account lifecycle and payouts as an explicit state machine

**States:** `evaluation(k)`, `funded_active`, `payout_pending`, `funded_locked_until_reset`,
`failed`, `passed_terminal`, `censored`.

**Order at an EOD boundary:**

1. EOD marks.
2. Threshold tests.
3. Pass conditions.
4. Payout eligibility.
5. Withdrawal.
6. Post-payout transitions: threshold reset, lock on the first payout, cycle counters reset.
7. Cap and consistency windows reopen.

The engine records every transition with its time and cause. A payout cycle is the span between
two withdrawals. Eligibility windows count since the last payout in their declared unit.

### 10. Commissions are part of the ruleset

- A ruleset carries `commissions`: per root, per side, in USD, by platform where they differ.
- The attempt uses the ruleset's commissions instead of the run's fee schedule. Spread and
  slippage still come from the run's cost schedule.
- **Unknown commissions are never treated as zero.**
  - A probability can be reported only as conditional on an explicit, named cost assumption.
  - Without one, the cost-dependent statistics are `unavailable`.
- Activation, monthly and reset fees are reported separately in the net economic value.

### 11. Mechanical simulation, conditional estimate, practical eligibility

Every attempt summary reports three separate things:

- **Mechanical outcome:** what the simulated account did under the modeled rules.
- **Estimate status:**
  - `complete` when every rule is modeled, verified and costed;
  - `conditional` when it depends on modeled rules only or on a cost assumption;
  - `partial` or `unavailable` when material values are unknown.
- **Practical eligibility:**
  - `eligible`;
  - `blocked_by_compliance`, which applies when a critical compliance rule such as Apex's ban on
    automated trading applies to the exact ruleset, plan and platform and to an automated
    strategy;
  - `unknown`.

A mechanically successful attempt under a compliance blocker is never reported as a practically
valid pass.

### 12. Economic-event calendar and news restrictions

**The calendar.** A historical, versioned economic-event dataset, built by the ingestion path in
AGENTS.md §14 from official sources. It covers at least FOMC, CPI and NFP. Each event row records:

- the source and URL;
- the event id and type;
- the scheduled publication instant and its time zone;
- the availability instant;
- the actual publication date;
- the record hash.

There are no hardcoded dates. Coverage gaps are explicit.

**The rule kind.** `news_restriction` declares:

- the event types;
- the restricted instruments;
- the pre-event and post-event windows;
- the scope: `new_entries`, `holding` or `all_trading`;
- the flatten behaviour.

A window that the calendar does not cover is `not_modeled` for that period. A material coverage gap
prevents a complete assessment.

### 13. Still `not_modeled` on OHLC bars

The following stay `not_modeled`, with their materiality carried into the status and the report:

- sub-minute holding-time and micro-scalping rules;
- cross-account hedging;
- the 2% price-limit restriction.

## Vocabulary added in C7b

These are generic kinds and parameters. Each comes with its own evaluator, hand-computed tests and
schema version 2.

**Payouts:**

- `max_usd`: a number or `unlimited`.
- `max_usd_by_payout`, a list of caps by payout number.
- `max_pct_of_balance` and `max_share_of_withdrawable`.
- `min_profit_since_last_usd` and a cumulative cycle goal.
- Windows that count since the last payout: profitable days, traded days, and consistency with
  `window: since_last_payout | all_time`.
- `first_payout_after_calendar_days`.
- `payout_group`, so that at most one path in a group pays at a close, chosen by the attempt
  policy.
- Post-payout effects on the threshold: `unchanged`, `reset_to_start`, `trail_from_new_balance`,
  `lock_on_first_payout`.

**Trailing:** `hwm_basis`, kept separate from the tested basis, and `lock.on: hwm | first_payout`.

**Daily loss:** amounts by balance tier, and a ratcheting limit set as a share of peak profit.

**Contracts:** `on_excess: clip | reject` on the scaling plan as well.

**Other kinds:**

- `daily_profit_cap`, with `forfeit_excess` or `promote_phase`.
- `flat_by` relative to the scheduled session end, so holiday early closes come from the CME
  calendar.
- `inactivity`: a maximum gap in trading days or calendar days, in a rolling window.
- Fees: `monthly`, counted per started calendar month of the attempt, and `on_reset`.
- `news_restriction` (section 12).

## Alternatives considered

- **Verification inside the content hash.** Rejected. Confirming a ruleset would change its
  identity and break immutability.
- **Non-overlapping starts only (every H-th date).** Rejected as the primary method. It throws away
  most of the information, and a block bootstrap over all starts handles the dependence. The
  `effective_independent_attempts` field states how much information there is.
- **Dropping censored starts silently, or counting them as fails.** Rejected. They are their own
  class, and the bounds show their possible effect.
- **One simulation per start including the signal.** Rejected. The signal is causal and independent
  of the account, so it is computed once.

## Consequences

- Firm rule data can change only by adding a version, and the owner's confirmation is a separate,
  hash-bound record.
- Every pass probability is labelled with its coverage, its counterfactual status and its
  verification status. No verdict is made.
- With overlapping attempts, intervals are wide on short windows. That is the honest amount of
  information, and the report says so.
