# ADR-0107: Firm rulesets as sourced, hash-locked data with owner-only verification; attempt sequences, censoring and pass probability with an overlapping-attempt block bootstrap

- **Status**: accepted
- **Date**: 2026-11-21

## Context

C7a (ADR-0106) built the generic rule engine and tested it on synthetic rulesets only. C7b adds
real firms and attempt statistics.

**Firms.** The owner ruled that all six firms are integrated at once: FTMO, Lucid, Topstep, Apex,
MyFundedFutures and FundedNext.

**Rule data.**

- Every value is loaded from versioned, sourced rule data. The engine never hardcodes one.
- A ruleset stays `unverified` until the owner confirms it.
- Old versions are immutable.

**Attempts.**

- An attempt starts on an eligible trade date.
- Attempts overlap, so they are not independent. Uncertainty comes from a block bootstrap on the
  start sequence, with blocks at least as long as the longest attempt horizon.
- Attempts that are right-censored at the end of the data form their own class.

**Time.**

- Market data stays strictly before 2025-01-01, and the vault stays closed.
- A current ruleset applied to that data is labelled a counterfactual application.

**Verdict.** None before C7e, so no threshold appears here.

## Decision

### 1. Where firm rulesets live, and how immutability is enforced

**Files.** Each ruleset is a file `rulesets/prop/<firm>/<ruleset_id>.v<N>.yaml`.

- The file sits at the repository root, outside the `crucible` package. It is data, not engine.
- `rulesets/prop/<firm>/RESEARCH.md` records every URL, quotation, snapshot file and hash, plus the
  values the official pages do not state.

**Snapshots.** The page snapshots themselves are kept privately, outside the repository. The
repository carries only their hashes and the short quotations.

**The lock.** `rulesets/prop/INDEX.json` is generated by `uv run python -m tools.docgen --write`.
It lists every `(ruleset_id, version, ruleset_sha256)`.

- A test recomputes every hash against INDEX.json.
- Editing a committed version fails the test. A change is a new file, `v<N+1>`.
- A version number can never be reused, and INDEX.json is append-only. A test compares it with the
  copy in git history.

**What the content hash covers.** `ruleset_sha256` hashes the content without the `verification`
block. Verification is a fact *about* a content hash, not part of it, so confirming a ruleset
never changes its identity.

### 2. Owner-only verification

**The sidecar.** Verification lives in a sidecar file,
`rulesets/prop/<firm>/<ruleset_id>.v<N>.verification.yaml`. It holds:

- `ruleset_sha256`;
- `status: verified`;
- `confirmed_by`, `confirmed_at` and `confirmation_note`;
- the list of rule ids the owner checked, which must be every rule.

**Reading the status.** A ruleset is `verified` only when a sidecar exists, its hash matches the
content and every attribution is complete and non-synthetic. Anything else is `unverified`, and
every result carries the status.

**Who writes the sidecar.** Only `crucible prop confirm <ruleset>` writes it.

- The command follows the ADR-0105 rule: interactive TTY only, and refused otherwise.
- It shows each rule with its quotation and URL.
- The owner must type the first 12 characters of the content hash.
- The research agent cannot run it. Like `vault set-admin`, it is the owner's step.

### 3. Vocabulary extensions

The firms' official pages name rules that C7a's vocabulary cannot express exactly. Each new kind or
parameter is added with its own evaluator, hand-computed tests and a schema version bump. The list
is fixed after the research step, in the section "Vocabulary added in C7b" below.

Any rule still outside the vocabulary stays `not_modeled`, with the materiality the owner confirms.

### 4. The attempt sequence

**Signal.** A prop evaluation reads one futures run configuration (ADR-0095). The strategy signal
is computed once over the window plus its warm-up, exactly as `run_futures` does. Targets do not
depend on the account, so one causal signal serves every start.

**Start dates.** Every Globex trade date `d` in the window whose first scheduled bar is tradable is
a start date.

**Each start.** `simulate_attempt` runs from the open of `d`, with a fresh account per phase.

- `max_horizon_trading_days` (H) is required, and refused if it is shorter than any phase's
  `max_trading_days`. A calendar-day limit is converted per start with the session calendar.
- Contracts come from the run's targets, so the account's rules clip or reject what the run asks
  for. The configuration records how the strategy is sized.

**Outcome classes, per start, for the evaluation:**

| Outcome | Meaning |
|---|---|
| `pass` | Every evaluation phase passed. |
| `fail` | A hard rule was breached. |
| `timeout` | The firm's own time limit ended the phase. |
| `horizon` | H was reached unresolved. This is the analyst's horizon, not a firm rule. |
| `censored` | The data end before `d + H` and before resolution. |

`censored` is never counted as a pass or a fail.

**Funded phase.** For starts that pass, the funded phase runs inside the same horizon. Its outcomes
are reported descriptively: survival, breach, payouts made, payout total, and fees. C7b states no
probability for funded profitability.

### 5. Pass probability and its uncertainty

**Complete starts.** These are the starts whose horizon fits in the data, `d + H ≤ last date`. They
are never censored.

**The estimate.**

- **Point estimate:** `p = passes / complete starts`.
- **Bounds over all starts:**
  - `p_low = passes / all starts`, treating censored starts as fails;
  - `p_high = (passes + censored) / all starts`, treating them as passes.

  These bounds are reported beside `p`.

**Bootstrap.** A seeded circular block bootstrap (ADR-0103) runs over the complete starts in date
order.

- The seed is `bootstrap_seed(evaluation_id, statistic)`.
- The block length is `max(H, ceil(sqrt(n)))` trading days. One block therefore always covers
  starts whose attempts can overlap.
- The statistics are `p` and the mean net cash per attempt: trader payouts minus fees, the fees
  including resets only when the attempt policy buys one.
- A 95% percentile interval is reported for each.
- With fewer than two blocks (`n < 2 × block`), the interval is `unavailable`, with the reason. No
  number is invented.

**Information.** `effective_independent_attempts ≈ n / H` is reported, so a reader sees how little
independent information overlapping starts carry.

**Status of a probability.** It inherits `evaluation_status` (ADR-0106):

- `complete`: it is a pass probability under the modeled rules.
- `conditional_on_modeled_rules`: it is reported under the field name `conditional_pass_probability`
  and labelled so.
- `blocked`: the number is still reported, under the same conditional name, with
  `definitive: false` and the critical rules listed.

Every result also carries `counterfactual_application`, the ruleset `as_of` and its effective
dates, and `unverified_ruleset`.

### 6. Entry points and artifacts

**Command.** `crucible futures prop --config <run.yaml> --ruleset <file> --horizon H
[--payout-policy max_eligible|none]` writes a sealed artifact `PRP-<16hex>` containing:

- `attempts.parquet`, one row per start: outcome, phase outcomes, breached rule and time, days to
  pass, minimum buffer, payouts, fees;
- `summary.json`, with the statistics, the bootstrap record and the coverage;
- `ruleset.yaml`, the exact copy used;
- the manifest, with the run id basis, the candidate id (ADR-0103) and the ruleset hash.

**Other entry points.** `crucible prop list` lists the rulesets with their verification status. The
MCP tools `crucible_futures_prop`, `crucible_prop_list` and `crucible_prop_validate` are also added.
`crucible prop confirm` is not exposed over MCP.

**Trials.** A prop evaluation is an evaluation of an existing candidate, not a new strategy trial.
It does not change `submission_count` or `total_trials`. It is linked to the candidate id and the
family.

**Vault.** A window that reaches the vault is refused by the guard (ADR-0105).

### 7. Evidence, assumptions, conflicts and scenarios (schema version 2)

Every rule declares an `evidence` field. It takes one of four values:

- `official_quote`: an attribution to an official page.
- `owner_provided`: the owner supplied it.
  - Example: Lucid's per-side commission table, pasted by the owner, saved privately and hashed.
  - The attribution names the URL the owner read, or `null`, and the snapshot hash of the saved
    text.
- `assumption`: one of the defaults below, named, with its rationale.
- `conflict_resolution`: a genuine conflict was resolved to the more restrictive reading.

**Conflicts.**

- Two sources count as contradictory only after checking that they refer to the same firm, plan,
  account size, phase, platform and effective period. Otherwise they are separate variants.
- A genuine conflict keeps **both** sources in `conflicts`, with the selected value, the
  alternative value or values, and the rationale.
- Each alternative becomes a named **sensitivity scenario**. The scenario is the ruleset with one
  conflict switched. It is simulated and reported beside the primary result, never as an official
  plan.
- An unresolved conservative choice is never presented as an officially confirmed rule.

**Defaults.** Each default is applied only where the firm is silent, and recorded as an
`assumption`:

- "EST" means `America/New_York`, including DST.
- An unspecified observation frequency means intraday.
- A profit target is tested on closed balance.
- A trading day is a trade date with at least one executed trade.

**Day units are distinct.** `calendar_days`, `trade_dates`, `trading_days` and `winning_days`
are separate units. A rule names its unit.

**Unlimited, unknown and not modeled are distinct.** A value is one of three things:

- a number;
- `unlimited`, which the source must state;
- `unknown`, a value the sources do not give, which makes the rule `not_modeled`.

Numeric sentinels are refused.

### 8. Every rule is a typed declaration

Each rule kind's schema makes every one of these explicit, with **no defaults** for firm
semantics:

- the metric and its basis: closed balance, equity, or day P&L;
- the threshold or formula;
- the observation frequency: `intraday`, `eod` or `on_request`;
- the reset boundary and its time zone;
- the trigger comparison: `<=`, `<`, `>=` or `>`;
- the resulting action or state transition: `fail`, `soft_lock_until_reset`, `liquidate`, `block_entries`,
  `promote_phase`, `forfeit_excess` or `none`;
- the source, the effective dates and the evidence.

The engine has no firm-specific branches. A test asserts this (ADR-0106).

### 9. Account lifecycle and payouts as an explicit state machine

**States:** `evaluation(k)`, `funded_active`, `payout_pending`, `funded_locked_until_reset`,
`failed`, `passed_terminal`, `censored`.

**Order at an EOD boundary:**

1. EOD marks.
2. Threshold tests.
3. Pass conditions.
4. Payout eligibility.
5. Withdrawal.
6. Post-payout transitions: threshold reset, lock on the first payout, cycle counters reset.
7. Cap and consistency windows reopen.

The engine records every transition with its time and cause. A payout cycle is the span between
two withdrawals. Eligibility windows count since the last payout in their declared unit.

### 10. Commissions are part of the ruleset

- A ruleset carries `commissions`: per root, per side, in USD, by platform where they differ.
- The attempt uses the ruleset's commissions instead of the run's fee schedule. Spread and
  slippage still come from the run's cost schedule.
- **Unknown commissions are never treated as zero.**
  - A probability can be reported only as conditional on an explicit, named cost assumption.
  - Without one, the cost-dependent statistics are `unavailable`.
- Activation, monthly and reset fees are reported separately in the net economic value.

### 11. Mechanical simulation, conditional estimate, practical eligibility

Every attempt summary reports three separate things:

- **Mechanical outcome:** what the simulated account did under the modeled rules.
- **Estimate status:**
  - `complete` when every rule is modeled, verified and costed;
  - `conditional` when it depends on modeled rules only or on a cost assumption;
  - `partial` or `unavailable` when material values are unknown.
- **Practical eligibility:**
  - `eligible`;
  - `blocked_by_compliance`, which applies when a critical compliance rule such as Apex's ban on
    automated trading applies to the exact ruleset, plan and platform and to an automated
    strategy;
  - `unknown`.

A mechanically successful attempt under a compliance blocker is never reported as a practically
valid pass.

### 12. Economic-event calendar and news restrictions

**The calendar.** A historical, versioned economic-event dataset, built by the ingestion path in
AGENTS.md §14 from official sources. It covers at least FOMC, CPI and NFP. Each event row records:

- the source and URL;
- the event id and type;
- the scheduled publication instant and its time zone;
- the availability instant;
- the actual publication date;
- the record hash.

There are no hardcoded dates. Coverage gaps are explicit.

**The rule kind.** `news_restriction` declares:

- the event types;
- the restricted instruments;
- the pre-event and post-event windows;
- the scope: `new_entries`, `holding` or `all_trading`;
- the flatten behaviour.

A window that the calendar does not cover is `not_modeled` for that period. A material coverage gap
prevents a complete assessment.

### 13. Still `not_modeled` on OHLC bars

The following stay `not_modeled`, with their materiality carried into the status and the report:

- sub-minute holding-time and micro-scalping rules;
- cross-account hedging;
- the 2% price-limit restriction.

## Vocabulary added in C7b

These are generic kinds and parameters. Each comes with its own evaluator, hand-computed tests and
schema version 2.

**Payouts:**

- `max_usd`: a number or `unlimited`.
- `max_usd_by_payout`, a list of caps by payout number.
- `max_pct_of_balance` and `max_share_of_withdrawable`.
- `min_profit_since_last_usd` and a cumulative cycle goal.
- Windows that count since the last payout: profitable days, traded days, and consistency with
  `window: since_last_payout | all_time`.
- `first_payout_after_calendar_days`.
- `payout_group`, so that at most one path in a group pays at a close, chosen by the attempt
  policy.
- Post-payout effects on the threshold: `unchanged`, `reset_to_start`, `trail_from_new_balance`,
  `lock_on_first_payout`.

**Trailing:** `hwm_basis`, kept separate from the tested basis, and `lock.on: hwm | first_payout`.

**Daily loss:** amounts by balance tier, and a ratcheting limit set as a share of peak profit.

**Contracts:** `on_excess: clip | reject` on the scaling plan as well.

**Other kinds:**

- `daily_profit_cap`, with `forfeit_excess` or `promote_phase`.
- `flat_by` relative to the scheduled session end, so holiday early closes come from the CME
  calendar.
- `inactivity`: a maximum gap in trading days or calendar days, in a rolling window.
- Fees: `monthly`, counted per started calendar month of the attempt, and `on_reset`.
- `news_restriction` (section 12).

## Amendment (2026-11-22): cost components and cost-assumption files

Section 10 above said a ruleset declares whether its per-side commission "includes the exchange and
regulatory fees" (`true | false | unknown`). The owner ruled that single flag wrong: a firm's
per-side commission is not one question but five components, and a boolean hides which of them is
unknown. This amendment replaces it in place (schema version 2 is unreleased), and states the
binding rules.

**1. Every cost component is recorded separately.**

- The components are: the brokerage **commission** (the firm's `per_side_usd`), the **exchange**
  fee, the **clearing** fee, the **nfa** assessment, and **other** (any other per-side charge).
- `commissions.components` is REQUIRED and has exactly those four keys (the commission is the
  `per_side_usd` itself), each `{status, evidence, text}`:
  - `included`: the firm's per-side commission contains the component. It needs a quotation that
    says so (`evidence: official_quote | owner_provided`).
  - `excluded`: the firm charges the component on top of the commission. It needs a quotation that
    says so.
  - `unknown`: the sources do not say. `evidence: not_stated` and `text` is a short note naming what
    was checked.
- There are no defaults: a missing key is refused. `commissions.includes_exchange_and_regulatory_fees`
  is refused BY NAME, with a message that names the new block.

**2. Unknown is never zero.**

- A component the sources do not state is `unknown`, and an `excluded` component with no covering
  row is unpriced: either is a GAP, never a zero.
- The cost total is never presented as complete while any component is unknown or unpriced: the
  attempt's `cost_status` is `unavailable`, and `cost_gaps` names each one.
- Firm commissions are not all-in unless the firm says so. Apex and Lucid are not all-in (every
  component `unknown`); Lucid's per-side table is `owner_provided`, pending independent
  verification, and is never described as all-in; FTMO gets no complete all-in cost while any
  required fee is missing.

**3. No universal CME fee, and no extrapolation.**

- A fee row prices only its exact root, `participant_type` and date range. There is no
  product-bucket-to-root mapping anywhere, and no fee is carried across roots, products or
  participant types.
- The owner's estimate of USD 1.38 per side is an **unverified owner reference**, recorded only in
  `docs/data/cme-exchange-fees.md` under "Unverified owner references". It is not a fee, no ruleset
  or module carries it, and the engine never reads it: it enters a run only through a
  cost-assumption file the user passes explicitly.

**4. The owner imports CME fee files.**

- Each row records the source (`source_url`, required), its effective dates, the product (root),
  the participant type, and which components the amount covers (`covers`, a `;`-separated list that
  must contain the row's own `fee_type`). A row covering several components is charged once.
- The rows are historical: a date picks its own row. The CME historical-fees page is required for
  pre-2025 data, and automated retrieval stays refused.
- `fee_rows_as_of(store, root, date, participant_type=..., components=...)` prices ONLY the root
  asked for. The earlier lookup demanded a row for every root and therefore could not use an owner
  file that priced one instrument; that was a bug, and a component with no covering row is now
  reported as a gap by the caller.

**5. The run states the participant type.**

- A ruleset never states one, so the participant type that prices `excluded` components is a RUN
  parameter (`--fee-participant-type`, MCP `fee_participant_type`). It is refused when missing as
  soon as a component is `excluded`.
- Using it makes the estimate `conditional`, with the reason `participant type assumed: <x>`. It is
  never `complete`.

**6. A cost assumption is a FILE, not a name.**

- Fields: `name`, `description`, `provided_by`, `status: unverified` (the only accepted value),
  `evidence`, and `amounts` keyed by root, each root a list of `{covers: [...], per_side_usd: "..."}`.
- An entry applies only to the root and components it lists: no extrapolation to another root.
- An `unknown` component it prices is ADDED, which is worse for the strategy and therefore the
  pessimistic direction.
- It may not override an `included` component, or an `excluded` one the dataset already priced:
  the run is refused.
- The assumption file's SHA-256, the gaps it priced and the gaps that remain are recorded in
  `attempts.parquet` (per component: status and USD, `cost_gaps`, `cost_assumption_sha256`,
  `fee_participant_type`), in `summary.json` (a per-component status table per root, plus the file's
  identity and its unused roots) and in the manifest.
- With every gap priced the estimate is `conditional` and never `complete`; with any gap left it is
  `unavailable`.

**Consequences of the amendment.**

- Six firm mappings were re-read against their own pages and rewritten: FundedNext (all four
  included, `other` unknown), Topstep (exchange and NFA included, clearing and other unknown), FTMO
  (exchange and NFA excluded, clearing and other unknown), and Apex, Lucid and MFFU (every
  component unknown — MFFU's former all-in reading rested on a column name and a subtitle that name
  no component separately, which is exactly the inference this amendment forbids).
- A cost-driven statistic now needs three explicit things from the user: the participant type, an
  owner fee file (or a dataset that prices the components), and — for anything a source leaves
  unknown — a cost-assumption file. Each is recorded by hash in the artifact.
- `rulesets/prop/INDEX.json` is regenerated: these rulesets are unverified and unmerged, so their
  content hashes change in place. The index stays append-only in the two senses that still hold: no
  version disappears, no version number is reused, and a `verified` ruleset's hash never changes.

## Amendment (2026-11-22, second): participant profile and other-fee evidence

The first amendment replaced one all-in flag with four cost components, and gave each fee row a
single `participant_type`. Two things were still wrong. A participant type is not one fact: the
exchange fee depends on CME membership, the NFA assessment depends on the bylaw's own subject (the
FCM member), and a charge can be the same for everyone. And an "other" row could be a catch-all: a
row typed `other` with a name like "misc" could add money nobody could point at, or a monthly
platform charge could arrive as a per-side execution cost. The owner ruled both out. This amendment
replaces the participant type with a run-level PROFILE resolved per component, and makes an `other`
row carry its own evidence.

**1. The run declares a participant profile; the classification is resolved per component.**

- A run declares an immutable `participant_profile`: a flat mapping from dimension name to value,
  e.g. `cme_membership_status: non_member` and `nfa_assessment_eligibility: fcm_member`.
- Dimension names are NOT an enum. Each row brings its own, and every name matches
  `^[a-z][a-z0-9_]*$`. Values are non-empty strings; the literal `unknown` is allowed and means
  *unknown*.
- A fee row declares the classification it needs: `classification_dimension` plus
  `classification_value`. They replace `participant_type`, and different components may need
  different dimensions (an exchange row `cme_membership_status=non_member`, the NFA row
  `nfa_assessment_eligibility=fcm_member`). A row that is the same for every participant uses
  `classification_dimension=none` / `classification_value=all`, which needs no profile entry.
- The former "an NFA row prices any participant type" pass-through is REMOVED: the profile must
  declare `nfa_assessment_eligibility`, or the `nfa` component is a gap. A classification the run
  never declared is not a classification the engine may assume.
- Resolution for an `excluded` component on `(root, date)`:
  1. take the rows that cover the component, for the exact root, with the date inside their
     effective range;
  2. look each row's dimension up in the profile: missing or `unknown` makes the component a gap
     whose reason is `classification <dim> not declared`; a different value means the row does not
     apply;
  3. exactly one applicable row prices the component; two are a refusal (ambiguous); none is a gap.
- There is never a default classification, and never a fallback to the only row available.
- The profile's canonical SHA-256 goes in the manifest, `summary.json` and every
  `attempts.parquet` row (`participant_profile_sha256`), and it is part of the evaluation id, so
  two profiles give two artifacts.
- The profile is the CLI's `--participant-profile FILE` (a flat YAML mapping) and the MCP tool's
  `participant_profile` object. It is required only when some component is `excluded`, and recorded
  when given either way.
- The estimate stays `conditional`, with the reason `participant profile declared by the run, not
  stated by the firm`. A profile is the run's declaration, never the firm's, so it never makes a
  cost `complete`.

**2. An `other` row must prove what it is.**

A row may carry `fee_type=other` ONLY with all of the following, each refused when missing or
empty:

- `charge_name`: a specific name or identifier. Generic names are refused case-insensitively after
  punctuation is stripped: `other`, `others`, `misc`, `miscellaneous`, `fees`, `other fees`,
  `cme other fees`, `additional fees`, `charges`, and any name made only of those words plus `cme`,
  `exchange` or `fee`/`fees`.
- `unit`: exactly `per_contract_per_side`. Monthly, platform, subscription and account charges are
  refused, with a message saying a fixed charge belongs in the ruleset's fee schedule, separate
  from execution costs.
- `source_url`: an official source; for a CME Group root, the host must be `www.cmegroup.com`.
- `quote`: the exact text naming the charge and its amount.
- `applies_quote`: the exact text showing the charge applies to this execution (product and
  participant).
- `distinct_from`: why the charge is not part of the exchange, clearing or NFA fee.
- `root`, `effective_from`, `classification_dimension` and `classification_value` — the
  classification being required unless the source states the charge is the same for every
  participant, in which case `none`/`all` needs no profile entry.

Further rules:

- `covers` must be exactly `other` for an `other` row.
- A row whose `fee_type` is `exchange`, `clearing` or `nfa` may NOT list `other` in `covers`: *an
  exchange fee cannot cover other components*. An `exchange` row may still cover
  `exchange;clearing` when the owner's source names both (CME's "Clearing & Trading").
- Two `other` rows with the same `charge_name`, root and classification that overlap in dates are
  refused: that is one charge written twice.
- Two `other` rows with DIFFERENT names covering the same date are both charged. They are distinct
  charges, each with its own evidence, and the `other` component is their sum — the one stated
  exception to "one row per component".
- `unit` is required on every row type, and only `per_contract_per_side` is accepted in this
  per-side table.

**3. Cost-assumption entries state their unit too.**

- Every amount entry now requires `unit: per_contract_per_side`; anything else is refused.
- An entry covering `other` also gives a `charge_name`, under the same generic-name refusal.

**4. What "all-in" can mean.**

`complete` is reached only when every applicable component is identified, quantified and backed by
evidence or an explicit assumption file. A profile-only resolution stays `conditional`. An
incomplete, explicitly conditional cost beats an apparently complete one.

**Consequences of the amendment.**

- `exchange_fees_v1`'s row contract changes shape (`participant_type` out;
  `classification_dimension`, `classification_value`, `unit`, `charge_name`, `applies_quote`,
  `distinct_from` in), and so does its stored sort order. The dataset is unreleased, so no committed
  artifact changes; see `docs/COMPATIBILITY.md`.
- `fee_rows_as_of` returns a `FeeLookup` (priced components plus a named reason per gap) instead of
  a bare mapping, because "absent" was a gap with no explanation and a gap must say what is missing.
- No ruleset changes: `commissions.components` already declares the four components, and the
  classification is a run input, not a firm value. `rulesets/prop/INDEX.json` is unchanged.
- The owner's fee file gains required columns: a supplier who used to write a participant type now
  writes the dimension and the value, and an `other` charge now has to be named and quoted twice
  (what it is, and why it applies).

## Amendment (2026-11-23): promotions, and what kind of default an assumption is

Two vocabulary gaps the Topstep review left open (F5, F6, F15). Neither changes a rule VALUE.

**1. A promotional value applies only when the run can show it bought that offer.**

The doubled per-request payout caps of the twelve daily-loss-limit files rest on a limited-time
offer. The offer is not the ruleset's value and it is not inferable: it depends on what the
participant bought. So a rule may carry ``promotions``, and each one states:

- ``id``; ``field`` (the numeric field it replaces: ``max_usd``, ``max_usd_by_payout[0]``,
  ``amount_usd``); exactly one of ``value`` or ``multiplier`` (the base value times it);
- ``starts_on`` and ``ends_on`` (``<date>`` or ``unknown``); ``purchase_on_or_after``;
- ``requires``, a mapping of participant-profile dimension to value, checked against the RUN's
  profile — account dimensions such as ``account_purchase: new``, ``dll_selected_at_purchase:
  'true'`` or ``purchase_date: YYYY-MM-DD`` are ordinary profile entries;
- ``source`` (an ``Attribution``), so the offer sentence is quoted like any other value.

Resolution is a pure function of the ruleset and the profile
(``crucible.prop.promotions.resolve_promotions``): a promotion applies only when EVERY requirement
is declared in the profile and matches, and the declared ``purchase_date`` falls in
``[starts_on, ends_on]``. ``ends_on: unknown`` is never assumed to continue past the ruleset's
``as_of``, so a purchase dated after it does not qualify. A missing, ``unknown`` or non-matching
fact leaves the BASE value in place — eligibility that cannot be shown is never assumed — and the
summary lists ``promotion <id> not applied: <reason>``. Two applicable promotions on one field are
refused (the value would depend on declaration order).

The promoted value is a property of the RUN, not of the file: the artifact still cites the
ruleset's own content hash, and ``attempts.parquet`` gains ``promotions_applied``
(``<id>:<rule>:<field>=<value>``, ``;``-joined, empty when none), with the applied and the skipped
lists in ``summary.json`` and the manifest.

For the Topstep files, the owner's decision is: the doubled cap applies ONLY when the account is a
NEW Trading Combine purchase, the daily-loss-limit add-on was selected at that purchase, and the
purchase date is on or after the offer start (2026-06-02); otherwise the standard cap applies. The
files themselves are not edited by this amendment — the promotion is declared where a file carries
the offer, and an ineligible run simply gets the standard cap with the reason recorded.

**2. Every assumption declares what KIND of default it is.**

An ``assumption`` entry gains a REQUIRED ``assumption_kind``: ``section7_default`` (the documented
default of ADR-0107 section 7), ``provisional_conservative`` (the source is silent or soft and the
pessimistic reading is temporary, open to being tightened) or ``owner_decision`` (the owner ruled
on it). A default that does not say what kind of default it is cannot be reviewed: the owner has to
re-check a "conservative" reading when the page softens, and never has to re-check a decision.

The owner ruled on the two Topstep readings:

- the ``profit_target`` EOD assumption (``unspecified_target_frequency_is_eod``) is
  ``provisional_conservative``: the page states the target without an observation frequency;
- the XFA inactivity close on day 31 is ``provisional_conservative``: the page says the account
  "may be closed", which is not a guaranteed automatic close. (No Topstep file carries this as an
  ``assumption`` entry: the rule is quoted and its pessimistic reading is in its description, so
  there is nothing to migrate for it. Reported, not edited.)

Mechanically every one of the 201 files was migrated: `section7_default` everywhere except the 98
``profit_target`` ``unspecified_target_frequency_is_eod`` entries, which are
``provisional_conservative``. No other value and no verification status changed. Because the files
are unverified and unmerged, their content hashes change in place and
``rulesets/prop/INDEX.json`` is regenerated; the append-only rule that matters is unchanged: a
version number never disappears or is reused, and a VERIFIED file's hash never changes (which is
what the lock test now asserts, as ADR-0107 section 1 states).

**3. Static threshold with an exact post-payout reset (reported, not built).**

Asked whether the engine supports a threshold that is static (never moving with equity highs or
daily closes) with an exact post-payout reset or lock, the answer is: **partly, and not for a
static threshold.**

- A static threshold exists (``static_drawdown``: ``start - amount``, never trailing) and is tested
  intraday and/or at the close like any other.
- Trail-freezing exists on the TRAILING rule: ``trailing_drawdown.lock`` with ``on: [hwm,
  first_payout]``, a trigger level (``at_balance_usd``/``at_offset_usd``) and an exact frozen level
  (``locked_threshold_usd``/``locked_offset_usd``), plus a payout-level override
  (``payout.threshold_after_payout: set_threshold`` with ``set_threshold_to: start |
  start_plus_usd:<x> | zero_balance_offset:<x>``).
- What is missing: a post-payout reset or lock ON a ``static_drawdown``. The payout's
  ``threshold_after_payout`` handler only reaches ``TrailingDrawdown`` instances, so a file that
  wants "static $2,000, reset to the start after a payout" has to express it as a trailing rule
  locked at the firm's form (which is what the Labs static file does today, flagged in its
  ``not_modeled`` entry), not as a static threshold. Implementing it would add a
  ``static_drawdown.lock`` vocabulary and its overlay handler; it is NOT implemented here.

## Amendment (2026-11-23, owner-review round 2): conditions, and what would change a materiality

Two vocabulary gaps the second pass over the Topstep packet left open (F13 and F21). Neither
changes a rule VALUE of an existing declaration.

**1. Practical eligibility gains `eligible_conditional`.**

Section 11 knew two answers: the account may be traded this way (`eligible`) or a critical rule
forbids it (`blocked_by_compliance`). A firm that allows automated trading only under obligations
no simulation can see answers neither: Topstep permits it through its API in the Trading Combine and
the XFA and forbids it in the Live Funded Account, prohibits high-frequency trading without stating
a threshold, requires every order to originate on the trader's personal device, forbids VPS/VPN or
remote-server order entry, and keeps the algorithm subject to every rule.

So a `compliance` rule may declare ``effect: condition`` with a required ``condition`` text, and:

- a critical rule with ``action: block`` that applies to the execution mode still wins:
  ``blocked_by_compliance``, no conditions listed (a block is a stronger statement than "you must
  also meet this");
- otherwise, when at least one applicable ``condition`` exists, practical eligibility is
  ``eligible_conditional`` and every condition is listed once, sorted, in
  ``AttemptResult.practical_eligibility_conditions``, ``summary.json`` and
  ``attempts.parquet``;
- a mechanical pass under a condition is counted in ``conditionally_valid_passes`` and NEVER in
  ``practically_valid_passes``: the simulation proved the account arithmetic, not the trader's
  compliance;
- ``effect: condition`` with ``action: block`` is refused (the two say opposite things about what
  the rule does), and the effect and its text are required together.

Authorization is not compliance: an API key, a subscription or an automated system is what the firm
grants, never evidence that a strategy obeys a rule. ``practical_eligibility(ruleset,
execution_mode)`` therefore returns a ``PracticalEligibility`` (``status``, ``conditions``,
``blocker``) rather than a bare string.

**2. An unmodeled entry states what would change its materiality.**

A ``not_modeled`` entry may declare ``becomes_immaterial_if``: the audited fact that would let its
materiality change. On a ``material`` entry it is the fact that could lower it ("an audit of the
instruments and dates shows it never affected a trade"); on an ``immaterial`` entry the same field
states what would make it bind ("becomes material if multiple accounts, copy trading or coordinated
strategies are simulated").

The declared materiality NEVER changes by itself: until an audit establishes the condition, the
conservative reading stands and the entry keeps weakening the estimate. The field is a statement of
what to check, not a self-service downgrade, and it is reported in ``rule_coverage``, in
``summary.json`` (``unmodeled_rules``) and in the firm's ``RESEARCH.md``.

**Mechanically**, the 201 unverified firm files were re-hashed in place (their dumps now carry the
optional fields), so ``rulesets/prop/INDEX.json`` is regenerated; no version number disappears or is
reused and no VERIFIED hash changes. ``attempts.parquet`` gains
``practical_eligibility_conditions`` and ``summary.json`` gains the eligibility block's
``conditions``/``conditionally_valid_passes`` plus ``unmodeled_rules``; both are additive.

## Amendment (2026-11-23, owner delegation, scaling-plan round): values printed only in an image

A firm publishes a rule the text never states. Topstep's XFA Scaling Plan is exactly that: the
article says the plan "sets your Maximum Position Size — the max contracts you can hold at one time
— based on your current account balance", and the ladder itself (balance bands against lots, per
account size) exists only inside a picture the page serves. Section 7's evidence vocabulary could
only say `not_modeled`, which is what the first four rounds did: a MATERIAL gap that overstated the
size a funded account may hold, in every file.

**1. `evidence: official_image_transcription`.** A rule whose value is printed only in an image
declares that evidence, and its `source` carries the image block: `image_snapshot_sha256` (the
file's own sha256), `image_path` (relative to the private snapshots root — absolute paths and `..`
are refused), `transcription` (the values exactly as printed, never a paraphrase of the page),
`transcribed_by` and `transcribed_at` (UTC). All five or none; the evidence and the block must agree
in both directions, so an image-only value can never be labelled `official_quote`.

**2. The self-check verifies the FILE, never the transcription.** `crucible.prop.sources` hashes the
snapshots folder, so every attribution's `snapshot_sha256` must resolve to a saved page and its
`quote` must appear in THAT page's text, and an image transcription's `image_path` must hash to
`image_snapshot_sha256`. A wrong hash is REFUSED (`DataQualityError`), not warned about, and
`crucible prop validate --snapshots-root DIR` runs the check. Nothing compares a transcription with
page text: there is none, which is the whole reason the type exists. A transcription is a named
person's reading of a picture, so it is checked for existence, completeness and the image's bytes —
the reading itself stays the owner's to confirm.

**3. `supporting_sources`, and `assumptions` as a list of named readings.** A rule carried ONE
`source`, so the page quotes that settle its basis, timing or units had nowhere to live: they ended
up paraphrased into a `description`, where the self-check could not see them. `supporting_sources`
is a list of attributions that support a rule WITHOUT carrying its value, held to the same standard.
And where one value depends on several named readings (a tier boundary, a silent case, an excess
action), `assumptions` carries each one by name beside the single `assumption` that makes a value
itself an assumption; `all_assumptions()` reports them, and names must be unique per rule.

**4. Balance tiers in `scaling_plan`.** The kind could only express profit rungs at `>=`, with a
lockout below the first rung — not an ABSOLUTE balance band, not a boundary that belongs to the
lower band, not a floor for a negative balance. It now can, additively:

- a step is keyed on `min_profit_usd` (the original form) or `min_balance_usd` (the absolute balance
  at the rule-day's close); a ladder may not mix them;
- the FIRST step may omit its threshold and is then the FLOOR rung: the size for every balance below
  the next threshold, which is how a negative or zero balance has a size instead of none;
- a balance ladder REQUIRES `basis: balance` and `evaluated: eod` (the tier is read at one close and
  applies to the whole next rule-day, so a mid-session reading would be a different rule) and takes
  its boundary from `comparison`: `>=` keeps a balance exactly on a threshold in the upper rung, `>`
  keeps it in the lower one. `<=` / `<` on an ascending ladder is refused by name;
- the profit form is untouched, INCLUDING its vestigial `comparison` (112 shipped rulesets declare
  `<=` while the engine has always applied `>=`): honouring it there would silently change every one
  of them, so the module's known gaps state that the field is meaningful only on a balance ladder.

The tier still changes only at `new_day`, so "the limit never rises mid-session" is structural, not
an assumption.

**Mechanically**, three additive fields (`supporting_sources`, `assumptions`, the image block on
`Attribution`) and one optional step key change no existing declaration of the 201 firm files; only
the 24 Topstep Trading Combine files gained a rule, and each was re-hashed in place, so
`rulesets/prop/INDEX.json` is regenerated and no verified hash changes.

## Amendment (2026-11-23, owner decision): an explicit upper-bound cost-assumption file

The per-firm cost-component table (`commissions.components` per firm file, priced per component where
a source exists) is the tracker of which firms have sourced costs, and it stays exactly as it is: it
will keep being filled with real data. What it cannot do is let a PRELIMINARY analysis run across
ALL firms today — a firm whose sources state nothing is a named gap, and a gap makes the cash
statistic `unavailable`, which is the correct answer and the wrong instrument for a first pass.

The owner therefore adds ONE explicit, versioned UPPER-BOUND cost-assumption file, and a `kind` on
every assumption file that says what its amounts claim. This is an addition to section 10 as the
2026-11-22 amendment rewrote it; nothing in that amendment is relaxed.

**1. `kind` is REQUIRED on a cost-assumption file: `point_estimate` or `upper_bound`.**

- `point_estimate` keeps the meaning the file already had: the owner's best single figure, naming
the costs it estimates. An amount that lands on a component the firm already has (`included`, priced
by the fee dataset, or a commission the firm states) is still a contradiction and is refused.
- `upper_bound` states CEILINGS. The file is a table over every root and component, so an amount that
lands on such a component is SKIPPED — never charged, never an error — because the bound fills only
the gaps. It never prices an `included` component, never a component the fee dataset priced, and
never a commission a firm states: those rules are enforced per component, not trusted.
- Either kind leaves the estimate `conditional`, never `complete`, and prices only gaps. A root the
file does not list stays a named gap: no extrapolation, ever.

**2. The artifact says what the cost is.** Under an `upper_bound` file:

- `summary.json` (top level and every scenario) and every `attempts.parquet` row carry
  `cost_bound: upper`;
- the cash statistic is labelled `lower_bound` — the cost is a ceiling, so the net cash can only
  rise once real costs arrive. It takes precedence over a payout cap's `upper_bound` label on the
  cash statistic, which applies to fewer attempts; the per-payout `bound` still reports
  `upper_bound`;
- the pass probability carries the reason `costs are an upper bound: the probability and the net cash
  are pessimistic (lower bounds) under it`, so a bound can never be read as a point estimate;
- every report carries the comparability note: *firms with fewer sourced cost components receive more
  of the bound, so cross-firm comparisons under it are pessimistic for the less documented firms*.
  A firm that states all of its components is charged none of the bound and a firm that states none
  is charged all of it, so the note is the honest reading of a cross-firm table under it.

**3. The file is data, versioned whole.** `rulesets/prop/cost_assumptions/upper_bound_v1.yaml` is
committed, `status: unverified`, `provided_by: owner`, and hashed like a ruleset: its `sha256` is an
entry of kind `cost_assumption` in `rulesets/prop/INDEX.json` (append-only, never edited in place
once merged) and is recorded in `summary.json`, the sealed manifest and every attempt row, and it is
part of the evaluation id. A change is a NEW file (`upper_bound_v2.yaml`), never an edit. It is NOT
`exchange_fees_v1`: it is not a fee table, no engine module or `docs/data/cme-exchange-fees.md` row
reads it, and its amounts are the owner's bounds, revisable when the real data arrive.

**Values (USD per contract per side, `unit: per_contract_per_side`).** ES/NQ/YM/RTY: exchange 2.00,
clearing 0.50, NFA 0.02, other 0.50. NKD: exchange 3.00, clearing 0.50, NFA 0.02, other 0.50.
MES/MNQ/MYM/M2K: exchange 0.60, clearing 0.25, NFA 0.02, other 0.25. The evidence text states the
rationale per row: Topstep publishes an ES exchange fee of $2.76 round turn (1.38 per side), which
matches the owner's 1.38 reference, plus margin; NKD is unknown, hence a wider margin; clearing and
`other` have no source and are deliberately generous bounds (the `other` entry is named
`unidentified_per_side_charges_upper_bound`); the NFA assessment comes from the NFA bylaw.

**Mechanically.** `CostAssumption` gains `kind` and its `cost_bound`; `validate`d file keys gain
`kind` (existing fixtures migrated); `AttemptResult`/`CommissionApplication` gain `cost_bound` and
`cost_assumption_kind`; `summary.json` gains `cost_bound`, `comparability_note` and
`cost_assumption.kind`; `attempts.parquet` gains the `cost_bound` column; `cash_estimate_status`
gains the `lower_bound` label; `rulesets/prop/INDEX.json` gains the assumption entry; `crucible prop
list` keeps listing rulesets only. Every one of those is additive: no released artifact changes, and
`/schema_version` stays where it is.

## Amendment (2026-11-24, Lucid review round): a material block is a CONDITION, and what the pages' words decide

The Lucid review (packet `internal/reviews/lucid.md`, F1-F33, delegated to the coordinator on

**1. A `material` + `action: block` compliance rule is an obligation, not a silence (F20).**

- `practical_eligibility` now lists, beside every `effect: condition` text, one entry per applicable
  `action: block` + `materiality: material` rule, as `<rule_id>: <restriction>` — the id a reader can

The Apex round made `consistency.comparison` meaningful. Lucid's own pages then decide each rule:

- "40% or less", "50% or less", "up to 50%" state an inclusive ceiling, so those rules keep `<=`;

zone (`reset.tz`, which is where a firm states its session times) and renders in that clock ("until

`test_the_entry_block_note_states_the_reopen_in_the_rules_own_clock` (2024-11-29, a 60-minute

## Amendment (2026-11-24, MFFU review round): a group phrase can state inclusion, and where a decision lives when no field carries it

The MyFundedFutures owner review (packet `internal/reviews/mffu.md`, F.1-F.35) settled 35 questions
over the 20 MFFU files. Two of them decide something a later firm will meet again; the rest are
declarations this ADR's vocabulary already carries. One of them needed an ENGINE change: F.6 (the
automation condition) is landed by the Lucid amendment above, and the MFFU files therefore carry no
`effect: condition` of their own - their five material bans condition the eligibility by the
engine's reading (four of them for `manual`).

**1. A group phrase in a firm's own subtitle is a statement of inclusion (F.1-F.5).**

MFFU publishes one number per contract, `Total Cost Round Trip`, and its subtitle says the column
"Includes Contract Specifications, Commissions, and Trading Fees". Section 10 asks an `included`

exchange fee and the NFA assessment it standardly denotes, so `exchange` and `nfa` are `included`
with the subtitle as their `text`, while `clearing` and `other` stay `unknown` because the subtitle
does not name them: inclusion is never inferred by association. The result is the treatment Topstep
already had, and under `upper_bound_v1.yaml` one ES side is `2.34 + 0.50 + 0.50 = 3.34` USD instead
of `5.36`. `tests/unit/test_prop_mffu_rulesets.py` pins that number against the committed bound
file, so the double count the packet measured (its section E.4) cannot come back silently.

**2. Where a decision lives when no field carries it.**

Three of the round's decisions have no per-rule field and are recorded outside the rulesets on
purpose, so the next reader knows where to look:

- a cost component's inclusion is the OWNER's call and `CostComponentDeclaration` has no
  `assumption_kind`: the decision and its arithmetic are the `commissions.source.section` prose, the
  YAML comment, `RESEARCH.md` and this amendment;
- the pessimistic breach-after-costs (F.32) is the ENGINE's reading of a firm whose page is silent
  (ADR-0106, `docs/TIMING.md`), so it is declared once for every firm here, not 20 times in a file;
- the automation condition (F.6) was a vocabulary change, and the Lucid amendment above landed it
  (a `material` + `block` rule conditions the eligibility of every mode it lists). This round adds no
  `effect: condition`, so the MFFU files needed no edit for it, and the reference run of `RESEARCH.md`
  section 12.1 reports the labels the engine now gives.

**3. What a re-quote is, and is not.**

Where an attribution quoted a sentence that does not contain the rule's own number (25 of them,
plus the Pro 100K/150K post-payout lock), the span is replaced by one that carries the number, in the
same page and the same snapshot; where no single span can carry every number of the rule, the missing
one becomes a `supporting_source`. No VALUE changes. The content hash does, because these files are
unverified and unreleased, so `rulesets/prop/INDEX.json` is regenerated: no version disappears or is
reused, and no VERIFIED hash changes.

**Mechanically.** The 20 files are re-hashed in place; the self-check now covers 866 attributions
(608 before) with 0 mismatches; `docs/modules/prop.md` states the group-phrase reading;
`docs/COMPATIBILITY.md` records the data (not vocabulary) change and the 5.36 -> 3.34 move; the three
Studio files keep every value because their only source page answers HTTP 404 (F.10), and drafting
the Signature successors is a recorded follow-up rather than part of this round.

## Alternatives considered

- **Verification inside the content hash.** Rejected. Confirming a ruleset would change its
  identity and break immutability.
- **Non-overlapping starts only (every H-th date).** Rejected as the primary method. It throws away
  most of the information, and a block bootstrap over all starts handles the dependence. The
  `effective_independent_attempts` field states how much information there is.
- **Dropping censored starts silently, or counting them as fails.** Rejected. They are their own
  class, and the bounds show their possible effect.
- **One simulation per start including the signal.** Rejected. The signal is causal and independent
  of the account, so it is computed once.

## Consequences

- Firm rule data can change only by adding a version, and the owner's confirmation is a separate,
  hash-bound record.
- Every pass probability is labelled with its coverage, its counterfactual status and its
  verification status. No verdict is made.
- With overlapping attempts, intervals are wide on short windows. That is the honest amount of
  information, and the report says so.
